01 / About

Reengineering and Documenting From Source Code

The Reengineering Toolkit (RET) analyzes existing Python source code and produces higher-level documentation describing its structure, functionality, and identifiable relationships — without executing or modifying the analyzed program.

Project motivation

Developers and other technically experienced users can struggle to understand codebases that are large, unfamiliar, poorly documented, or no longer accompanied by accurate design documentation. Manually tracing relationships between components takes significant time. RET reduces this difficulty by automatically recovering useful structural information from Python source code as a higher-level starting point — not a replacement for detailed source inspection.

System concept

RET accepts a Python project through its CLI, parses eligible source files into Abstract Syntax Trees (ASTs), and analyzes them to identify program components and relationships.

Python Project→AST Analysis→Structure→Docs + UML
02 / Goals

What the system should help users do

01

Analyze Python projects

Support multi-file Python projects containing up to 700 combined lines of source code across one to five files.

02

Explain structure

Identify modules, packages, classes, functions, methods, variables, imports, and docstrings.

03

Generate UML diagrams

Create class, sequence, and dependency diagrams using applicable UML notation when sufficient information is available.

04

Build confidence

Keep analysis local so proprietary source code is not transmitted to external services.

Key findings

Start with the big pictureUsers want a plain-English project overview before reading individual files or looking at diagrams.
Relationships matterDependencies and program flow are the hardest parts to trace manually — especially across modules and services.
Visuals help — especially sequence flowSequence diagrams showing request flow were repeatedly cited as more useful than detailed class diagrams.
Traceability builds trustInaccurate generated documentation is worse than none — users will abandon a tool that "lies" about what code does.
Keep analysis local on the CLIProprietary source code cannot leave the network. The initial RET release stays command-line and local.

07 / Development plan

From source code to understanding

The RET is organized into modules that directly reflect the needs identified during user research and the constraints defined in the SRS.

01

RET CLI & Project Input

Command-line interface to supply a Python project, initiate analysis, report errors, and access generated results.

02

Input Validation & File Discovery

Validate the supplied project and identify analyzable Python .py source files while rejecting non-Python files.

03

AST Construction

Parse eligible Python source files into Abstract Syntax Trees without executing the analyzed program.

04

Construct & Relationship Analysis

Identify modules, packages, classes, functions, methods, imports, inheritance, and statically identifiable calls.

05

RET Reporter & Output

Generate human-readable documentation and applicable class, sequence, and dependency diagrams. Export organized results.

Stage 1

Requirements → Design → Implementation

The Stage 1 work establishes the user needs and software requirements that will guide later design, implementation, testing, and demonstration of the Reengineering Toolkit.
